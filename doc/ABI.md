# Sketch: a portable C ABI for `lo` bindings

## Goal

Right now every binding — whether statically linked (`core`, `curl`, `system`,
...) or `dlopen`'d as a separate `.so` (`luajit`, `python`, ...) — talks
directly to V8's C++ API: `v8::Isolate`, `v8::Local<v8::Value>`,
`v8::FunctionCallbackInfo`, `v8::CFunction`/`CTypeInfo`, etc. That's fine
while there's only one engine, but it means every binding is inherently
V8-only.

The goal here is a small, stable, `extern "C"` boundary — no C++ types cross
it, everything engine-specific is an opaque pointer — such that:

- a binding compiled against this ABI keeps working unmodified against any
  `lo` build that implements it, whether that build embeds V8, JSC, or
  QuickJS;
- the ABI surface is exactly what would be exported in the `EXPORTS=abi`
  build mode from [`PROPOSAL.md`](PROPOSAL.md) — this doc and that one
  describe the same boundary from two angles (export-size vs.
  engine-portability).

This is a sketch to drive discussion, not a final spec — options are laid
out with tradeoffs where the design isn't settled yet.

## Where V8 actually shows up today

Traced this by grepping every `lib/*/api.js` for raw `v8::` code and reading
[`lib/gen.js`](../lib/gen.js), the codegen that turns `api.js` definitions
into the `.cc` files that get compiled per binding.

### The "simple" bindings — no V8 code of their own

The large majority of bindings (`epoll`, `mach`, `kevents`, `system`,
`curl`, `sqlite`, `boringssl`, `net`, `zlib`, `md4c`, `ada`, ... — everything
under `lib/*/api.js` **without** a `v8::`-containing `preamble`) are pure
data: `{ parameters: [...], result: '...', pointers: [...] }` per function,
plus `constants`/`structs`/`includes`. None of that data mentions V8 at all.

**All** the V8-specific code for these bindings is generated by exactly one
piece of code: [`lib/gen.js`](../lib/gen.js)'s `bindings()` function. For
every function it always emits the same shape — a `*Slow` function using
`v8::FunctionCallbackInfo<Value>`/`Local<Integer>::Cast(...)`/`String::Utf8Value`/
`args.GetReturnValue().Set(...)`, and (unless `nofast`/`slow` is set) a
`*Fast` function paired with a `v8::CFunction`/`CTypeInfo` for V8's
[Fast API Calls](https://v8.dev/blog/fast-api-calls). Registration goes
through `SET_METHOD`/`SET_FAST_METHOD`/`SET_VALUE`/`SET_MODULE` — thin
`lo::`-namespaced helpers already declared in [`lo.h:109-122`](../lo.h#L109-L122),
implemented in `lo.cc` — and each binding's `.cc` ends with:

```cpp
extern "C" { DLL_PUBLIC void* _register_<name>() { return (void*)Init; } }
```

That entry point is resolved (via `modules_add`'s static table for built-in
bindings, or `dlsym` for `.so` ones — see `load()` in
[`main.js:162-193`](../main.js#L162-L193)) and called from
[`lo::Library()`](../lo.cc#L668-L692), which does:

```cpp
auto _register = reinterpret_cast<InitializerCallback>(_init());
_register(isolate, exports);   // InitializerCallback = void(*)(Isolate*, Local<ObjectTemplate>)
```

So the actual boundary every binding crosses is narrow and consistent:
**one entry-point signature** (`Init(Isolate*, Local<ObjectTemplate>)`) and
**one codegen template** producing V8-typed argument unwrapping. Neither is
scattered per-binding — which is the encouraging finding here: fixing
`lib/gen.js`'s template and this one entry-point signature makes every
"simple" binding portable, with zero changes to any `api.js` file.

Also worth noting: `lo.h`'s `FastTypes` enum
(`i8, i16, i32, u8, u16, u32, empty, f32, f64, u64, i64, iSize, uSize,
pointer, buffer, function, u32array, boolean, string`) is *already* a
reasonably engine-neutral type-tag vocabulary — it's not V8-shaped, it's
just "native C types plus a few JS-bridging conveniences (`string`,
`buffer`, `pointer`)." This is a good candidate to become the ABI's
canonical type system rather than inventing a new one.

### The real special cases — raw `v8::` in `preamble`

Four `api.js` files embed literal C++ into their generated `.cc` via a
`preamble` field (spliced in verbatim by `lib/gen.js`), and that C++ touches
`v8::` types directly:

- **[`lib/core/api.js`](../lib/core/api.js#L460-L746)** (and its Windows
  variant, [`lib/core2/api.js`](../lib/core2/api.js), same code duplicated) —
  this is the big one. Its preamble implements `bind_fastcallSlow`/
  `bind_slowcallSlow`/`SlowCallback`/`CTypeFromV8`: it **dynamically
  constructs** a `v8::CTypeInfo`/`CFunctionInfo`/`CFunction`/
  `FunctionTemplate` *at runtime*, from a `struct fastcall` descriptor
  (function pointer + result type tag + array of parameter type tags) that
  JS builds up. This is what backs [`lib/ffi.js`](../lib/ffi.js)'s `bind()`
  — the mechanism that lets arbitrary `dlopen()`'d C functions get
  registered as fast-callable JS functions at runtime, using the exact same
  `FastTypes` tag vocabulary mentioned above.
- **[`lib/libffi/api.js`](../lib/libffi/api.js#L25-L426)** — the same
  dynamic-`CFunction`-construction pattern, but built on top of real
  `libffi` (`ffi_prep_cif`/`ffi_call`) instead of `lo`'s own hand-rolled
  x64/arm64 JIT assembler ([`lib/asm/*`](../lib/asm)) for the actual call.
  A second implementation of the same idea.
- **[`lib/heap/api.js`](../lib/heap/api.js)** — genuinely V8-only:
  `v8::HeapProfiler`, `v8::HeapSnapshot`, `v8::OutputStream`. There's no
  portable equivalent to propose here; this should stay an explicit,
  engine-specific extension rather than something the ABI tries to unify
  (see [Engine-specific extensions](#engine-specific-extensions-not-unified)).

The important realization from reading `core`'s preamble closely: **this
"special case" is not a one-off hack, it's a working prototype of exactly
the generic, tag-driven dispatch mechanism this ABI needs** — it already
does, dynamically, exactly what the codegen'd simple bindings do statically.
That overlap is why the two design options below aren't as different as
they first look.

## Design principles

- **Pure C, `extern "C"` everywhere.** No C++ types, no exceptions, no
  templates cross the boundary. Anything engine-specific — the isolate/JS
  context, a JS value, the current call's arguments — is an opaque pointer
  (`typedef struct lo_engine lo_engine_t;` with no visible definition, per
  engine backend).
- **One calling convention, not two.** Today's codegen always produces a
  `*Slow` (works always) and `*Fast` (V8 Fast-API-only) pair per function.
  JSC and QuickJS have no equivalent to V8's compile-time-declared
  monomorphic native fast-call mechanism, so baking that split into the ABI
  itself would bake a V8-specific concept into a "portable" layer. Proposed
  resolution: **the ABI exposes exactly one call shape**; whether a given
  engine backend internally does something fast-API-like for it is that
  backend's private implementation detail, invisible to binding authors.
  (V8's backend is free to still build a `CFunction`/`CTypeInfo` under the
  hood — see the performance discussion below.)
- **Handle lifetimes are explicit.** A `lo_value_t*` handle is valid only
  for the duration of the current native call by default (mirrors
  `v8::Local`'s handle-scope lifetime, and is compatible with how JSC/
  QuickJS manage GC roots too, even though the mechanisms differ
  underneath). Anything that needs to outlive one call needs an explicit
  `lo_value_ref()`/`lo_value_unref()` pair (mirrors `v8::Global`/JSC's
  `JSValueProtect`/QuickJS's `JS_DupValue`+refcounting) — never a bare
  pointer kept around past the call that produced it.
- **No C++ exceptions cross the boundary.** Errors are a return code plus
  `lo_engine_throw(engine, message)` to set a pending JS exception the
  engine backend raises on return — V8's `TryCatch`, JSC's
  `JSValueRef* exception` out-param, and QuickJS's `JS_Throw`/exception
  value are different enough mechanisms that trying to unify them as
  anything richer than "here's a message, go throw it" isn't worth it.

## Sketch of the header

```c
// lo_abi.h — illustrative, not final

typedef struct lo_engine   lo_engine_t;    // one per isolate/context
typedef struct lo_value    lo_value_t;     // opaque JS value handle
typedef struct lo_args     lo_args_t;      // opaque "current call" handle
typedef struct lo_module   lo_module_t;    // opaque "exports object under construction"

// canonical type tags — extends today's lo.h `FastTypes` enum
typedef enum {
  LO_I8, LO_I16, LO_I32, LO_U8, LO_U16, LO_U32, LO_VOID, LO_F32, LO_F64,
  LO_U64, LO_I64, LO_ISIZE, LO_USIZE, LO_POINTER, LO_BUFFER, LO_FUNCTION,
  LO_U32ARRAY, LO_BOOL, LO_STRING
} lo_type_t;

// argument/return accessors — the one calling convention
DLL_PUBLIC int32_t   lo_arg_i32(lo_args_t*, int index);
DLL_PUBLIC uint64_t  lo_arg_u64(lo_args_t*, int index);
DLL_PUBLIC void*     lo_arg_pointer(lo_args_t*, int index);
DLL_PUBLIC const char* lo_arg_string(lo_args_t*, int index, uint32_t* len_out);
/* ... one accessor per lo_type_t ... */
DLL_PUBLIC void lo_return_i32(lo_args_t*, int32_t);
DLL_PUBLIC void lo_return_pointer(lo_args_t*, void*);
/* ... */
DLL_PUBLIC void lo_engine_throw(lo_engine_t*, const char* message);

// module construction
DLL_PUBLIC lo_module_t* lo_module_new(lo_engine_t*, const char* name);
DLL_PUBLIC void lo_module_set_i32(lo_module_t*, const char* name, int32_t);
DLL_PUBLIC void lo_module_set_u64(lo_module_t*, const char* name, uint64_t);
/* covers today's `constants`/`structs` (sizeof) codegen, which is already
   engine-agnostic in spirit — see initConstant/initStruct in lib/gen.js */

// entry point every binding exports — resolved by name, same convention as
// today's `_register_<name>`, but with a portable signature instead of a
// `void*` that gets cast to a V8-typed function pointer
typedef int (*lo_register_fn)(lo_engine_t*, lo_module_t*);
```

Dropping the current double indirection (`_register_<name>()` returns a
`void*` that gets `reinterpret_cast` to `InitializerCallback`) is possible
now specifically *because* the signature is engine-neutral — that
indirection existed to avoid naming a V8-typed function pointer in a header
meant to be `extern "C"`-safe; once the params are opaque handles, the
function can just be named directly:

```cpp
extern "C" DLL_PUBLIC int lo_register_epoll(lo_engine_t* engine, lo_module_t* module);
```

## The open question: how functions actually get registered

Two ways to get from an `api.js` definition to a working native function,
laid out with tradeoffs since this is the part still worth debating.

### Option 1 — generic descriptor + one shared trampoline (leaning this way)

`lib/gen.js` stops emitting per-function C++ entirely. Instead it emits one
static data table per binding, and the engine backend interprets it
generically at registration time:

```c
typedef struct {
  const char* name;
  lo_type_t   result;
  const lo_type_t* params;
  uint8_t     nparams;
  void*       fn;      // ordinary C function pointer, e.g. int32_t f(int32_t,int32_t)
  uint32_t    flags;
} lo_fn_desc_t;

DLL_PUBLIC int lo_register_functions(lo_engine_t*, lo_module_t*,
  const lo_fn_desc_t* fns, uint32_t count);
```

```cpp
// what lib/gen.js emits for the whole epoll binding, generated code shown in full:
static const lo_fn_desc_t epoll_fns[] = {
  { "create", LO_I32, (lo_type_t[]){LO_I32}, 1, (void*)create, 0 },
  { "wait",   LO_I32, (lo_type_t[]){LO_I32,LO_POINTER,LO_I32,LO_I32}, 4, (void*)wait, 0 },
};
extern "C" DLL_PUBLIC int lo_register_epoll(lo_engine_t* e, lo_module_t* m) {
  return lo_register_functions(e, m, epoll_fns, 2);
}
```

This is, functionally, **the exact mechanism `core`'s existing
`bind_fastcall`/`bind_slowcall`/`SlowCallback` already implements for
`dlopen`'d FFI libraries** — generalized so that compiled-in bindings and
runtime-`dlopen`'d C libraries go through the same registration path, one
with a descriptor known at compile time, one built at runtime by
[`lib/ffi.js`](../lib/ffi.js). `core`'s "special case" stops being a
one-off and becomes the reference implementation.

**Pros**

- Real engine-agnosticism: adding a new engine backend means implementing
  *one* generic dispatcher (`lo_register_functions`, walking the tag array)
  plus the accessor primitives — not re-deriving what `lib/gen.js`'s
  template should emit for that engine.
- `lib/gen.js` shrinks to "emit a data table" — no engine knowledge in the
  codegen at all. Matches "as simple as possible."
- One code path to fix bugs in (argument coercion, string handling) instead
  of N generated functions per binding.
- Directly unifies with the FFI path that already exists and is exercised
  (`test-ffi.js`, `sum.c`) — not a new, unproven mechanism.

**Cons**

- A generic trampoline walking a tag array in a loop is inherently less
  specialized per-call than a hand-generated monomorphic function — this is
  the exact perf difference `test-ffi.js` already measures between `sum`
  (fast) and `sum_slow` (slow) in this repo today. Naively, Option 1 risks
  giving every binding the "slow path" characteristics permanently.
  - **Mitigation, and it's a strong one**: this codebase already has the
    tool to fix this — [`lib/asm/*`](../lib/asm) + `lib/asm/compiler.js`'s
    `mmap`+`mprotect` JIT. `lo_register_functions` can, at registration
    time, JIT a specialized trampoline per descriptor exactly the way
    `lib/ffi.js`'s `compile_fastcall` already does for arbitrary FFI calls
    — generic *input* (the descriptor table), specialized *output* (a
    JIT'd trampoline per function), same as today's FFI path. This isn't
    hypothetical; it's the same trick already in production in this repo,
    just applied to compiled-in bindings instead of only `dlopen`'d ones.
  - This needs actual benchmarking once built — flagged here, not claimed
    as solved.
- Less debuggable in the "read the generated .cc" sense — a binding's
  dispatch logic isn't visible as readable per-function C++ anymore, just a
  data table plus a shared interpreter/JIT. (`lo gen` could still print a
  resolved, human-readable dump of a binding's table for inspection.)
- Commits the whole ABI to expressing every signature in the `lo_type_t`
  vocabulary — anything outside it (structs by value, multiple return
  values, callback parameters beyond the existing `function` tag) still
  needs the `preamble` escape hatch, same as `core`/`heap`/`libffi` today.
  Not a new problem, but Option 1 makes the tag vocabulary's completeness
  more load-bearing since it's the *only* path, not one of several.

### Option 2 — keep codegen'd wrappers, retarget the types

`lib/gen.js` keeps its current shape (`getFastFunctionDecl`/`getFunction`
emitting a `*Slow` and `*Fast` function per API entry), just swaps every
`v8::`-typed call for an `lo_*` ABI call:

```cpp
// lib/gen.js still emits, per function:
void createSlow(lo_args_t* args) {
  int32_t v0 = lo_arg_i32(args, 0);
  int32_t rc = create(v0);
  lo_return_i32(args, rc);
}
```

**Pros**

- Smaller diff from today's `lib/gen.js` — same control flow, same
  per-function shape, lower risk of behavior regressions during migration.
- Each function stays a small, specialized, easily-inlined native function
  — no generic type-switch loop on the hot path, so today's performance
  characteristics carry over close to as-is (modulo the accessor-call
  indirection, which is trivially inlinable).
- Generated `.cc` output stays human-readable and steppable in a debugger,
  same as today.

**Cons**

- Doesn't actually decouple `lib/gen.js` from having an opinion about
  engine call shape — it still needs to know "emit a Slow variant and
  (conditionally) a Fast variant," which is a V8-shaped concept
  (compile-time-declared monomorphic native fast-call) with no clean
  analog in JSC or QuickJS. A QuickJS backend would likely implement the
  `*Fast` accessor calls identically to `*Slow` — meaning the Fast/Slow
  split becomes dead duplication for non-V8 engines, unless `lib/gen.js`
  is taught to skip emitting it per target engine (more branching, more
  places for engine-specific logic to leak back into supposedly-portable
  codegen).
- Every binding still produces 2×N generated functions in the compiled
  binary — doesn't reduce `lib/gen.js`'s ~675 lines of templating logic or
  the amount of generated code much; the "one engine backend implements one
  thing" simplicity of Option 1 doesn't apply here (each engine backend
  instead implements O(type-tag) accessor primitives, which is smaller in
  isolation, but `lib/gen.js` itself stays a full templating system that
  needs to understand casts/overrides/pointer types in detail).

### Where this leaves it

Given the stated goal — engine-agnostic above all, simple, willing to pass
opaque pointers rather than avoid any indirection — **Option 1 is the
better fit**, on the condition that the perf mitigation (JIT a specialized
trampoline per descriptor at registration time, reusing `lib/asm/*`) is
taken seriously rather than assumed. That mitigation isn't speculative
engineering — it's the same mechanism `lib/ffi.js` already uses in
production for FFI calls, just applied one level up. Worth prototyping
Option 1 against one real binding (e.g. `epoll`, small and self-contained)
and benchmarking it against today's codegen'd version before committing
runtime for a full migration.

## Engine-specific extensions (not unified)

`lib/heap/api.js`'s `v8::HeapProfiler`/`HeapSnapshot` usage has no
cross-engine equivalent and shouldn't be forced into one. Proposed
treatment: bindings like this stay outside the portable ABI entirely and
are conditionally built only for the engine(s) they apply to (the existing
`runtime/*.config.js` mechanism already selects which bindings get linked
in per build — extending it with an engine-capability check is a small,
separate piece of work, not addressed further here).

## Relationship to `PROPOSAL.md`

The `lo_*` symbols sketched here are exactly the export surface
`PROPOSAL.md`'s `EXPORTS=abi` mode is built around — once this ABI exists,
`lo.exports`/`lo.dynsym` in that proposal are simply "every `lo_*` symbol
declared in `lo_abi.h`." The two pieces of work compose directly: this doc
defines *what* stays exported, that one defines *how* everything else gets
hidden.

## Not addressed here

- Exact accessor list for every `lo_type_t` (illustrative subset shown above).
- ABI versioning/negotiation story (a version field the loader checks before
  calling `lo_register_*`, most likely) — needed before this ships, not
  designed here.
- Windows story — no dynamically-loaded addon mechanism analogous to
  `-bundle_loader`/`-rdynamic` currently exists for the Windows build (see
  the same open item in `PROPOSAL.md`); out of scope for this pass.
- Migration plan / sequencing for porting `core`'s FFI preamble itself onto
  whichever option is chosen — nontrivial given it's the mechanism
  everything else in this doc leans on, deserves its own pass once an
  option is picked.
